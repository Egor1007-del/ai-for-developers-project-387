## Сценарий бронирования

1. Владелец создаёт тип встречи, указав название, описание и длительность.
2. Гость без регистрации выбирает тип встречи и открывает календарь на ближайшие 14 дней.
3. Гость выбирает свободный слот и подтверждает запись без ввода личных данных.
4. Гость видит подтверждение встречи, а занятое время становится недоступным для других записей, включая встречи других типов.
5. Владелец видит новую встречу в списке предстоящих записей всех типов.

## Установка

Необходим [mise](https://mise.jdx.dev/) для установки инструментов, указанных в `mise.toml`.
Также установите утилиту командной строки `sqlite3`: Rails использует её для загрузки и сохранения SQL-схемы базы данных (например, `sudo apt install sqlite3` в Debian/Ubuntu).

```bash
git clone https://github.com/Egor1007-del/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise install
mise run setup
```

## Использование

```bash
mise run dev
```

Откройте http://localhost:3000: оттуда доступны запись на встречу и раздел владельца. Прямые адреса: http://localhost:3000/booking и http://localhost:3000/admin.

Проверка состояния приложения: http://localhost:3000/up.

### Production Docker

Для запуска нужна доступная PostgreSQL-база и секретный `SECRET_KEY_BASE` (например, результат `mise exec -- bin/rails secret`). Передайте строку подключения через `DATABASE_URL`. Если PostgreSQL работает в отдельном контейнере, подключите оба контейнера к одной Docker-сети (например, созданной командой `docker network create calendar-network`) и укажите имя контейнера PostgreSQL как хост в `DATABASE_URL`, а не `localhost`. В примере ниже PostgreSQL уже подключён к сети `calendar-network`.

```bash
docker build -t calendar-calls .
docker run --rm --network calendar-network -p 3000:3000 \
  -e DATABASE_URL="$DATABASE_URL" \
  -e SECRET_KEY_BASE="$SECRET_KEY_BASE" \
  -e PORT=3000 calendar-calls
```

Контейнер слушает `0.0.0.0` на порту `PORT` (по умолчанию 3000). При старте выполняются подготовка базы и seeds: недостающие начальные типы событий создаются по названию и длительности, существующие записи не перезаписываются. Данные сохраняются между перезапусками, пока сохраняется сама база PostgreSQL.

Для автоматической проверки контейнер можно запустить только с `PORT=8080`: если `DATABASE_URL` и `SECRET_KEY_BASE` не заданы, он использует SQLite в `/tmp` и случайный секрет. Эти данные и секрет временные и не предназначены для production. Если задана только одна из двух переменных, запуск завершится ошибкой.

### Деплой и диагностика Render

`render.yaml` описывает бесплатный Docker-сервис в Oregon, использующий существующую базу `calendar-calls-db`. Blueprint подключает `DATABASE_URL` из базы и генерирует `SECRET_KEY_BASE`; секреты не нужно помещать в репозиторий. Сервис отслеживает только `main` и настроен на **After CI Checks Pass**.

Перед подтверждением Blueprint проверьте план в Render Dashboard: он должен создавать только веб-сервис и ссылаться на существующую базу. После публикации изменений убедитесь, что GitHub Actions действительно запустил и успешно завершил все три задания CI на коммите `main`: SQLite checks, PostgreSQL checks и Production Docker. Render также считает результаты `skipped` и `neutral` успешными; сам по себе включённый режим ожидания CI не гарантирует запуск каждого задания.

При сбое проверьте статус задания в GitHub Actions, затем Deploys, Events и логи сборки и приложения в Render Dashboard. Проверьте доступность PostgreSQL, настройки окружения и ответ `/up`. Не публикуйте значения переменных окружения и секреты в логах или отчётах.

#### Истечение срока базы и восстановление работы

Данные хранятся в Render Postgres и сохраняются при перезапуске или повторном деплое веб-сервиса, пока сохраняется сама база. Файловая система бесплатного веб-сервиса временная и для хранения данных не подходит. Бесплатная база Postgres истекает через **30 дней после создания**, а не после последнего перезапуска. Проверьте дату создания и срок действия конкретной базы в Render Dashboard. После истечения база недоступна; согласно [ограничениям Render](https://render.com/docs/free#30-day-limit), в течение 14 дней её можно перевести на платный тариф, а затем Render удаляет её вместе с данными.

Резервные копии для этой бесплатной базы не предусмотрены. Следующая процедура восстанавливает **работу приложения на пустой базе**, а не прежние данные: созданные владельцем типы событий и записи гостей в новую базу не попадут. Само истечение срока ещё не означает их удаление, но удаление старой базы уничтожит их безвозвратно.

1. В Render Dashboard выберите нужный workspace, проверьте состояние `calendar-calls-db` и дождитесь завершения уже запущенной синхронизации Blueprint. Отключите **Auto Sync** у Blueprint до любых изменений в его Git-ветке и до ручного изменения `DATABASE_URL`: иначе синхронизация может примениться автоматически и перезаписать значение. Это отдельная настройка от автодеплоя веб-сервиса.
2. В workspace может быть только одна активная бесплатная база Postgres. Если старая база занимает этот слот, для создания новой её потребуется удалить; удаление необратимо и уничтожает все оставшиеся данные.
3. Создайте в том же workspace новую Render Postgres с тарифом Free и регионом Oregon, как у веб-сервиса. Дождитесь готовности базы. На странице базы в разделе Connect скопируйте **Internal Database URL**; это секрет, не помещайте его в репозиторий и сообщения.
4. На странице веб-сервиса `calendar-calls` в Environment замените `DATABASE_URL` на скопированный URL новой базы и сохраните изменение с перезапуском/деплоем. Существующий `SECRET_KEY_BASE` сохраняйте. Если выбрано сохранение без деплоя, запустите деплой вручную.
5. Дождитесь успешного запуска и проверьте логи. При стандартной команде Docker `./bin/rails server` entrypoint запускает `db:prepare`, затем `db:seed`: схема подготавливается, а начальные типы «Знакомство» и «Обсуждение» создаются, если отсутствуют. При переопределённой команде запуска эта автоматическая подготовка может не выполниться. Откройте https://calendar-calls-t97n.onrender.com/up и само приложение, проверьте отображение начальных типов и работу записи. При ошибке проверьте Deploys и логи, доступность базы, регион и `DATABASE_URL`.
6. При выключенном Auto Sync согласуйте Blueprint с новой базой: `render.yaml` задаёт `DATABASE_URL` через `fromDatabase` с именем `calendar-calls-db`, но саму базу в разделе `databases` не создаёт. Если имя новой базы отличается, измените ссылку на её имя в `render.yaml` и опубликуйте изменение в Git-ветке Blueprint. Не помещайте URL в файл. Если имя совпадает, изменение файла может не понадобиться.
7. Вручную запросите план синхронизации Blueprint и проверьте результат **до применения**: ссылка должна указывать на новую существующую базу, а план не должен содержать нежелательных изменений или создания лишних ресурсов. При ошибке планирования или неверном плане не применяйте его: исправьте конфигурацию и запросите новый план. Если изменений нет, подтверждать нечего; всё равно проверьте фактическое подключение к новой базе. Если план корректен и содержит изменения, подтвердите его применение и дождитесь завершения синхронизации.
8. Проверьте после синхронизации, что `DATABASE_URL` указывает на новую базу, деплой успешен и приложение работает. Только после этого при необходимости включите Auto Sync обратно: последующие изменения Blueprint из Git могут применяться автоматически.

На бесплатном тарифе Render позволяет откатиться к двум последним предыдущим деплоям. Откат приложения не откатывает базу данных: перед откатом проверьте совместимость предыдущего кода с текущей схемой и миграциями. После ручного деплоя конкретного коммита проверьте настройку автодеплоя: некоторые способы ручного деплоя отключают её.

### Render MCP в OpenCode

Проектный `opencode.json` подключает [hosted Render MCP](https://render.com/docs/mcp-server) по HTTPS с API-ключом из переменной окружения. Формат `mcp.render` совместим с OpenCode 1.19.6 и поддерживается текущей [схемой OpenCode](https://opencode.ai/config.json) как устаревший; в [документации V2](https://opencode.ai/docs/mcp-servers/) используется `mcp.servers.render`.

1. Если `RENDER_API_KEY` уже доступна процессу OpenCode, используйте существующую переменную. Иначе создайте API-ключ в [настройках аккаунта Render](https://dashboard.render.com/u/settings?add-api-key) и введите его в Bash без отображения и без сохранения в истории команд:

   ```bash
   read -r -s -p 'Render API key: ' RENDER_API_KEY
   export RENDER_API_KEY
   ```

   Не помещайте ключ в файлы проекта, сообщения или логи. Переменная должна быть доступна процессу OpenCode; по завершении работы можно выполнить `unset RENDER_API_KEY`.
2. Запустите OpenCode из этого же терминала в корне проекта. После изменения конфигурации или переменной полностью перезапустите OpenCode.
3. В том же терминале выполните `opencode mcp list`: у `render` должен быть статус `connected`. Этот статус сам по себе не подтверждает действительность ключа: проверьте доступ следующим шагом. При ошибке проверьте наличие переменной, доступность сети и права аккаунта Render, не выводя значение ключа.
4. В OpenCode попросите агента вызвать `list_workspaces`, подтвердите workspace `collective_blog` и попросите перечислить его сервисы (`list_services` с `workspaceId` выбранного workspace). Это проверка чтением без изменения ресурсов. Не публикуйте вывод, если он содержит конфиденциальные данные.

Render MCP предоставляет доступ к ресурсам аккаунта, включая операции изменения и деплоя. Используйте ключ только с доверенным клиентом и проверяйте запрашиваемые действия. OpenCode 1.19.6 при проверке чистой OAuth-авторизации сообщил, что сервер авторизации не поддерживает динамическую регистрацию клиента; поэтому здесь используется API-ключ.

### Фоновый запуск через mise daemons

Альтернативный способ запуска сервера и сборки JavaScript и стилей — фоновые процессы под управлением pitchfork. Поддержка daemons в mise является экспериментальной; она включена в конфигурации проекта. При первом запуске mise установит закреплённую версию pitchfork, если она ещё не установлена.

```bash
mise daemons start   # запустить web, js и css
mise daemons status  # проверить состояние
mise daemons logs    # посмотреть вывод процессов
mise daemons stop    # остановить процессы
```

Оба способа запуска используют порт 3000, поэтому перед переключением остановите работающий сервер.

### OpenCode в GitHub Actions

Workflow `.github/workflows/opencode.yml` запускает OpenCode для помощи с задачами и кодом по комментариям в issue и pull request, включая комментарии к строкам кода. Поддерживаются упоминания `/oc` и `/opencode`, например:

```text
/oc explain this issue
```

Запуск доступен доверенным участникам с правом записи; комментарии ботов и PR из форков исключены. Агент использует бесплатную на момент настройки модель `opencode/deepseek-v4.1-flash-free` через OpenCode Console; её доступность и лимиты могут измениться. Для запуска нужны установленное GitHub App OpenCode Agent и секрет Actions `OPENCODE_API_KEY` с ключом Console. Ключ не помещается в репозиторий.

Агент отвечает комментарием в issue или PR; в зависимости от задачи он может изменить ветку PR или создать ветку и PR для issue. Состояние и журналы доступны во вкладке GitHub Actions, ссылка на запуск включается в ответ агента. Одновременные запросы к одной issue или PR выполняются последовательно; тайм-аут задания — 15 минут.

OpenCode обнаруживает проектные skills из `.agents/skills`. Workflow проверяет обнаружение skill `implement` после checkout; использование конкретного skill зависит от запроса и решения модели.

#### Автоматический и ручной triage обращений

Workflow `.github/workflows/opencode-triage.yml` запускается при открытии Issue (`issues: opened`). До запуска модели он допускает только пользователей типа `User` с отношением к репозиторию `OWNER`, `MEMBER` или `COLLABORATOR`; боты и другие авторы пропускаются. OpenCode также проверяет, что инициатор имеет право `admin` или `write`. Допускаются Issue без triage-метки или с `needs-triage`; `needs-info`, `ready-for-agent`, `ready-for-human` и `wontfix` исключают запуск даже при наличии `needs-triage`. Обычные метки категорий этой проверке не мешают. Подготовленные проектными skills спецификации и тикеты получают `ready-for-agent` и потому пропускаются.

Перед checkout workflow повторно проверяет актуальные метки и открытое состояние Issue. Метки могут измениться и после этой проверки; prompt просит агента перепроверить их перед действиями, но полностью исключить гонку это не позволяет. Изменение меток или ответ автора сами по себе новый автозапуск не инициируют. События, созданные с помощью стандартного `GITHUB_TOKEN`, обычно не запускают другие workflow; см. [документацию GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow).

Агент использует skill `triage`: изучает обращение и приложение, ищет существующую реализацию и похожие обращения, классифицирует запрос, задаёт вопросы, назначает метки и рекомендует следующий шаг. Ответ публикуется в Issue. При недостатке информации он может назначить `needs-info`; решение о закрытии остаётся за сопровождающим. Ручной triage доступен через существующий workflow: доверенный участник может оставить в Issue комментарий `/oc используй triage для этого обращения`. Для последующей обработки `needs-info` после ответа автора используйте ручной запуск.

Автотриаж использует закреплённые версии инструментов из `mise.toml` и ручного workflow, основную модель `opencode/deepseek-v4.1-flash-free`, вспомогательную `opencode/mimo-v2.6-flash-free`, секрет `OPENCODE_API_KEY` и тайм-аут 15 минут. Запуски одного workflow для одной Issue выполняются последовательно. Для прямой команды `opencode github run` версии 1.19.6 инструкция задаётся переменной `PROMPT`, как следует из [исходного кода версии](https://github.com/anomalyco/opencode/blob/v1.19.6/packages/opencode/src/cli/cmd/github.handler.ts); в [документации GitHub-интеграции](https://opencode.ai/docs/github/) для GitHub Action используется вход `prompt`.

Автоматический workflow передаёт `GH_TOKEN` и `GITHUB_TOKEN` с правами только `contents: read` и `issues: write`, а также включает `USE_GITHUB_TOKEN: true`. Поэтому он не обменивает OIDC-токен на токен OpenCode GitHub App: разрешения установленного App на запись кода и PR не наследуются этим запуском. Ручной workflow продолжает использовать App и его отдельные разрешения. `issues: write` необходимо для комментария и меток, но позволяет и другие операции с Issue; prompt запрещает создавать спецификации и тикеты, изменять код, создавать коммиты и PR. OpenCode создаёт временную локальную ветку для обработки Issue; прав на публикацию ветки у токена нет.

Текст Issue, комментарии и ссылки считаются недоверенными данными, а не инструкциями. Prompt требует игнорировать содержащиеся в них команды и не раскрывать секреты; текст Issue не вставляется в shell-скрипт. Фильтрация авторов, ограниченный токен и закрепление действий уменьшают риск, но prompt не гарантирует защиту от внедрения инструкций. См. [рекомендации GitHub по безопасности Actions](https://docs.github.com/en/actions/reference/security/secure-use).

Проверить после публикации workflow в ветке по умолчанию можно на тестовых Issue: открыть обращение доверенным автором без triage-метки и с `needs-triage`; убедиться в анализе и метках. Отдельно проверить каждую исключающую метку, конфликт меток, автора без доверенного статуса и бота — модель запускаться не должна. Проверить уже реализованную функциональность, неполное обращение и текст с посторонними инструкциями; просмотреть комментарий и журнал Actions, отсутствие новых Issue и PR и изменений кода. Метки нужно назначить при создании Issue или до повторной проверки workflow. Проверить ручной triage можно комментарием `/oc` в существующем Issue.

В `.github/jactionlint.yaml` согласовано исключение правила `dangerous-triggers` только для `.github/workflows/opencode.yml`, до **24 февраля 2027 года**. Событие `issue_comment` необходимо для команд в issue, а доступ к запуску ограничен доверенными пользователями, проверкой прав и исключением PR из форков. Остаточный риск: агент может встретить недоверенные инструкции в содержимом issue или его комментариях. Исключение и меры защиты нужно пересмотреть к указанной дате. Показать все диагностики без исключений: `mise exec -- jactionlint --no-ignores`.

JavaScript собирается командой `mise exec -- yarn build`, а TypeScript проверяется командой `mise exec -- yarn typecheck`. Новые Stimulus-контроллеры нужно импортировать и регистрировать в `app/javascript/controllers/index.js`. Rails автоматически собирает ассеты при запуске тестов и `assets:precompile`.

При `mise run setup` устанавливаются Git-хуки hk: перед коммитом запускается RuboCop, а сообщение проверяется на соответствие Conventional Commits (например, `feat: добавить календарь`). Для повторной установки хуков выполните `mise exec -- hk install --mise`.
